# 자유일정 패키지 숙소 자동 추가

## 1. 목적

자유일정 패키지를 처음 생성할 때 TourAPI 숙박 데이터에서 숙소 한 곳을 자동으로 선택한다.

선택된 숙소는 사용자가 이후 관광지나 음식점을 수정하더라도 변경하지 않는다. 숙소는 일정 전체에서 한 곳만 사용하며, 화면과 DB에도 한 번만 표시한다.

자유일정 가격은 당일치기는 무료, 숙박 일정은 포함 숙소의 추정 숙박비만 받는다.

## 2. 적용 기준

| 여행 기간 | 숙소 적용 방식 |
|---|---|
| 당일치기 | 숙소를 추가하지 않음 |
| 1박 2일~4박 5일 | TourAPI 숙소 한 곳을 최초 생성 시 선택 |

- 4박 5일 일정도 숙소를 여러 곳으로 나누지 않는다.
- 숙소는 최초 일정 생성 시에만 결정한다.
- 관광지·음식점·액티비티를 수정해도 기존 숙소를 유지한다.
- 숙소는 일차별 관광 일정과 분리해 일정 최상위 정보로 한 번만 저장한다.

## 3. 숙소 선택 방식

### 3.1 후보 데이터

`tour_recommender` DB의 `places` 테이블에서 TourAPI 숙박 데이터만 조회한다.

```text
content_type_id = 32
```

다음 조건을 만족하는 데이터만 후보로 사용한다.

- 숙소명이 존재함
- 위도와 경도가 존재함
- 위도와 경도가 0이 아님
- TourAPI 숙박 유형임

숙소 이미지는 `place_images` 테이블에서 대표 이미지 한 장을 조회한다.

### 3.2 거리 계산

최초 생성된 일정에 포함된 관광지·음식점·액티비티의 좌표를 모두 수집한다.

각 숙소 후보에서 전체 일정 장소까지의 거리를 Haversine 방식으로 계산하고, 평균 거리가 가장 짧은 숙소를 선택한다.

```text
숙소 점수 = 전체 일정 장소까지의 평균 거리
```

평균 거리가 동일한 후보가 있다면 대표 이미지가 존재하는 숙소를 우선한다.

이 방식은 첫날 마지막 관광지에만 가까운 숙소를 고르는 것이 아니라, 전체 여행 동선에서 접근하기 좋은 숙소 한 곳을 선택하기 위한 방식이다.

## 4. 생성 흐름

```text
사용자 여행 조건 입력
        ↓
RAG·LLM 일정 생성
        ↓
OR-Tools 관광지 순서 최적화
        ↓
전체 일정 좌표 수집
        ↓
TourAPI 숙소 후보 조회
        ↓
전체 장소와 평균 거리가 가장 짧은 숙소 선택
        ↓
엔진 상태에 고정 숙소 저장
        ↓
일정 최상위 hotel 정보로 숙소 한 번 저장
```

## 5. 숙소 데이터 구조

선택한 숙소는 일정 엔진 상태의 `hotel` 필드에 저장한다.

```json
{
  "hotel": {
    "content_id": 123456,
    "title": "제주 오션뷰 호텔",
    "address": "제주특별자치도 서귀포시 ...",
    "latitude": 33.123456,
    "longitude": 126.123456,
    "thumbnail_url": "https://...",
    "nights": 2,
    "source": "tourapi",
    "is_fixed": true
  },
  "days": []
}
```

| 필드 | 설명 |
|---|---|
| `content_id` | TourAPI 장소 식별자 |
| `title` | 숙소명 |
| `address` | 숙소 주소 |
| `latitude` | 위도 |
| `longitude` | 경도 |
| `thumbnail_url` | 대표 이미지 |
| `nights` | 숙박 일수 (`여행 일수 - 1`) |
| `source` | 데이터 출처 |
| `is_fixed` | 일정 수정 시 유지되는 숙소인지 표시 |

## 6. DB 및 API 저장 방식

숙소는 `travel_itineraryitem`에 저장하지 않는다. 일차별 장소인 `days[].items`와 분리하여 `Itinerary.engine_state` 내부의 최상위 `itinerary.hotel`에 한 번만 저장한다.

```text
Itinerary.engine_state
└─ itinerary
   ├─ hotel
   │  ├─ content_id
   │  ├─ title
   │  ├─ address
   │  ├─ latitude
   │  ├─ longitude
   │  ├─ thumbnail_url
   │  ├─ nights
   │  ├─ source
   │  └─ is_fixed
   └─ days
```

일정 조회 API에서는 `hotel`을 `days`와 같은 최상위 응답 필드로 제공한다.

```json
{
  "hotel": {
    "content_id": 123456,
    "title": "제주 오션뷰 호텔",
    "nights": 2
  },
  "days": []
}
```

프론트에서는 숙소를 DAY 1 장소 목록에 넣지 않고, 일차별 일정과 분리된 `포함 숙소` 카드로 한 번만 표시한다.

## 7. 일정 수정 시 숙소 유지

기존 일정 수정 로직은 일차별 항목을 삭제한 뒤 수정된 일정으로 다시 저장한다. 따라서 숙소를 일반 일정 항목으로만 저장하면 수정 과정에서 사라질 수 있다.

이를 방지하기 위해 다음 순서로 처리한다.

1. 수정 전 엔진 상태에서 `hotel` 정보를 별도로 보관한다.
2. LLM을 이용하여 관광지·음식점 등의 일정을 수정한다.
3. 수정된 엔진 상태에 기존 `hotel` 정보를 다시 적용한다.
4. 수정된 엔진 상태의 최상위 `hotel` 필드에 동일한 숙소를 다시 저장한다.

따라서 사용자가 관광지나 음식점을 수정해도 숙소의 `content_id`, 이름, 위치는 변경되지 않는다.

## 8. 변경 파일

숙소 선택 및 저장 로직은 다음 파일에 추가했다.

```text
backend/apps/travel/services.py
```

주요 추가 기능은 다음과 같다.

- TourAPI 숙소 후보 조회
- Haversine 거리 계산
- 전체 일정 기준 숙소 한 곳 선택
- 최초 생성 시 고정 숙소 저장
- 일차별 장소와 분리된 최상위 `hotel` 데이터 저장
- 일정 수정 시 기존 숙소 보존

## 10. 자유일정 가격 정책

기존의 `추천 패키지 가격 + 12%` 방식은 사용하지 않는다. 관광지와 음식점 일정 자체에는 비용을 부과하지 않는다.

| 구분 | 1인 가격 |
|---|---:|
| 당일치기 | 무료 (0원) |
| 일반 숙소 | 70,000원 × 숙박 수 |
| 상급 숙소 | 110,000원 × 숙박 수 |
| 고급 숙소 | 175,000원 × 숙박 수 |

숙소 객실은 2인 1실을 기준으로 하며, 기존 패키지 데이터 생성에 사용한 객실 추정가를 동일하게 적용한다.

```text
1인 가격 = 객실 1박 추정가 × 숙박 수 ÷ 2명
```

- 일반 객실: 140,000원/박
- 상급 객실: 220,000원/박
- 고급 객실: 350,000원/박
- TourAPI가 실시간 객실 가격을 제공하지 않으므로 현재 가격은 추정가이다.
- 유사한 기존 패키지가 검색되지 않아도 자유일정 상품은 독립적으로 제공한다.

## 11. 현재 제외된 내용

다음 내용은 이번 작업에 포함하지 않았다.

- 숙소 실시간 객실 조회
- 숙소 실시간 예약 가능 여부
- 실제 숙박 가격 조회
- 사용자의 숙소 직접 변경 기능
- 여러 숙소를 사용하는 일정

TourAPI에는 정확한 실시간 객실 가격과 재고가 없기 때문에 가격 및 실제 예약 연동은 별도의 정책이나 외부 예약 API가 필요하다.
